## 二、研究问题和总体思路

本项目研究的是 Execution-Trust Bias：Python 代码能够成功执行，并不意味着它正确理解了问题。传统的 Python agent 往往把“没有异常”当成成功，但它可能使用了错误列、漏掉过滤条件、选错实体、把行数当成去重后的数量、使用错误的聚合函数、把最大值和最小值方向弄反，或者最终返回中间表而不是问题要求的答案。

第二篇方法保留第一篇数据处理和执行基础，只修改推理后的检查和修复部分。每个样本首先生成 Question Intent IR，记录任务类型、答案类型、答案基数、目标列、过滤条件、聚合、排序、比较和布尔极性。随后模型生成 Python，代码经过受控执行得到结果；代码不会只交给语言模型解释，而是同时使用 Python AST、Pandas 操作模式、运行时结果、表结构、真实单元格值以及数值、日期和字符串归一化信息构造 Code Intent IR。

执行成功后，审计器按三个独立粒度检查代码是否忠实执行了问题意图：

1. Global Intent Alignment 检查任务级别是否一致，例如问题要求布尔判断时是否返回布尔值，问题要求一个答案时是否返回整张表或多行集合，问题要求计数时是否把结果错误地当成普通查找。
2. Operator Logic Alignment 检查操作逻辑是否一致，例如过滤、聚合、排序、排名、算术、比较和最终返回操作是否存在、方向是否正确、顺序是否合理。
3. Parameter & Entity Alignment 检查参数和实体是否落在真实表上，例如使用的列名、筛选实体、比较值、比较符号、布尔极性、排序列和答案目标是否与问题及表格相符。

三层审计分别有代码结构、日志字段、异常类型和开关，不是只写在 prompt 中。审计发现异常后生成通用 repair hint，调用模型进行有限次数的 targeted repair，重新执行并重新审计。修复只有在重新执行成功且新审计不再报告语义异常时才接受；不能因为代码“能运行”就接受修复。运行时还记录空结果、空集合、None、NaN、空字符串、返回整张表以及缺少 DataFrame 证据等信号。

本方法借鉴了两篇知识图谱论文中的 Generate–Verify–Refine 和 Planning–Coding–Execution–Evaluator 思路，但研究对象不同：知识图谱方法主要不信任逻辑形式或路径是否有效，本项目进一步检查“已经成功执行的 Python 是否语义正确”。借鉴内容包括有限迭代预算、局部操作验证、异常/空结果触发反思、评估器决定是否继续和完整记录修复轨迹；没有把知识图谱的路径验证机械搬到表格任务中。

## 三、三种实验方法

`baseline` 是严格对照：DeepSeek-V3.2 生成 Python，使用同一 Python executor 执行，再使用同一 WTQ/TabFact evaluator 评测。不使用语义审计修复。

`audit` 是第二篇核心方法：Python 生成、成功执行后进行 Global、Operator、Parameter 三层审计；发现语义异常时执行有限次定向修复、重新执行和重新审计。

`joint` 是准确率导向的联合配置：同时生成直接文本推理候选和 Python 候选，使用规范化后的候选一致性、表格 grounding、问题类型、数值证据以及 audit-aware selector 选择答案。TabFact 的 Yes/No/True/False/1/0 会统一归一化，避免仅因为候选字符串类型不同而选错。joint 用于提高准确率和作为联合推理消融，不替代 baseline 与 audit 的严格主比较。

支持的消融开关如下：

- `--audit-level global`：只运行 Global 审计。
- `--audit-level global_operator`：运行 Global 和 Operator 审计。
- `--audit-level full`：运行 Global、Operator、Parameter 三层审计。
- `--audit-mode hybrid`：AST、grounding、runtime trace 与必要的 LLM 语义判断结合。
- `--audit-mode llm_only`：只使用 LLM 审计，作为消融配置。

## 四、运行入口和数据区间

工作目录固定为：


API 配置从环境变量读取：`PARATERA_API_KEY`、`PARATERA_BASE_URL`、`MODEL_ID`。服务器上也配置了权限为 600 的 `.secrets/paratera.env` 备用文件；密钥不会写入代码、日志、`result.jsonl` 或本说明。

运行前 100 条的脚本入口是：

```bash
bash scripts/run_100_all.sh
```

它会按顺序运行 WTQ baseline、WTQ audit、WTQ joint、TabFact baseline、TabFact audit、TabFact joint，避免同一输出目录被并发写入。默认区间是 `[0,100)`，即 flat index 0 到 99。可以指定新的实验根目录，避免覆盖已有结果：

```bash
EXPERIMENT_ROOT=100_cycle3 bash scripts/run_100_all.sh
```

也可以单独运行某个方法：

```bash
EXPERIMENT_ROOT=100_cycle3 bash scripts/wtq_baseline_0_100.sh

EXPERIMENT_ROOT=100_cycle3 bash scripts/wtq_joint_0_100.sh
EXPERIMENT_ROOT=100_cycle3 bash scripts/tabfact_baseline_0_100.sh
EXPERIMENT_ROOT=100_cycle3 bash scripts/tabfact_audit_0_100.sh
EXPERIMENT_ROOT=100_cycle3 bash scripts/tabfact_joint_0_100.sh
```

任意起点和终点使用通用脚本，终点是开区间：

```bash
EXPERIMENT_ROOT=slice_10_20 bash scripts/run_range.sh wtq baseline 10 20 slice_10_20
EXPERIMENT_ROOT=slice_100_110 bash scripts/run_range.sh tabfact audit 100 110 slice_100_110
```

实际运行文件是 `scripts/run_paper1.py`。脚本参数还可以直接指定 `--audit-level`、`--audit-mode`、`--max-repairs`、`--dp-votes`、`--timeout` 和 `--overwrite`。固定区间 wrapper 只是为了让数据集、方法和区间一目了然。

## 五、输出文件如何查看

当前推荐查看目录是：

```text
outputs/100_cycle1_clean/     第一轮 100 条干净结果，joint 为当前最佳准确率
outputs/100_cycle2_clean/     第二轮修改后的 100 条干净结果，用于迭代比较
```

每个数据集和方法目录都有以下文件：

- `config.json`：本轮模型、方法、区间、审计配置、修复次数和样本 ID。
- `selected_samples.json`：实际使用的 sample ID，保证 baseline、audit、joint 成对可比。
- `result.jsonl`：每行一个样本的完整结构化记录。
- `log/<flat_index>.txt`：第一篇项目兼容的逐条文本日志，并追加执行、三层审计和修复信息。
- `summary.json`：准确率、执行成功率、静默错误数量、审计异常、分层错误、API 调用数和延迟。
- `cache/`：模型响应缓存，用于复现实验和减少重复 API 调用。
- `RESULT_INDEX.md`：该实验根目录的汇总索引。

`result.jsonl` 保留第一篇项目的核心字段：`idx`、`answer`、`text`、`transpose`、`resort`、`question_id`、`table_id`、`title`、`table`、`question`。其中 WTQ 和 TabFact 的 loader、表格序列化、问题与答案 ID 对齐、归一化和 evaluator 都沿用了第一篇项目对应实现。

在这些字段后，第二篇追加：`sample_id`、`method`、`selected_method`、`route`、`generated_python`、`execution_result`、`execution_error`、`execution_success`、`initial_execution_success`、`final_execution_success`、`final_execution_result`、`execution_warnings`、`question_intent_ir`、`code_intent_ir`、`global_audit`、`operator_audit`、`parameter_audit`、`semantic_logic_exception`、`semantic_exception`、`semantic_exception_detail`、`repair_hint`、`repaired_code`、`repair_trace`、`repair_count`、`dp_answer`、`agent_answer`、`selection`、`initial_answer`、`initial_correct`、`final_answer`、`normalized_prediction`、`correct`、`model`、`api_usage`、`api_calls` 和 `latency_seconds`。

查看单条结果时，先看 `question`、`answer`、`generated_python`、`execution_success`、`execution_result`、`final_answer` 和 `correct`；研究语义错误时再看三层 audit、`semantic_exception_detail`、`repair_trace` 和 `execution_warnings`。查看某类错误时可以按 `error_type` 搜索 `global_audit`、`operator_audit` 和 `parameter_audit`。

## 六、100 条实验结果

第一轮干净结果 `outputs/100_cycle1_clean`：

| 数据集 | Python baseline | Semantic audit | Joint 最终配置 | baseline 执行成功率 | baseline 静默错误候选 |
|---|---:|---:|---:|---:|---:|
| WTQ | 67% | 66% | 83% | 82% | 22 |
| TabFact | 87% | 83% | 92% | 98% | 12 |

第一轮中，baseline 静默错误定义为 `execution_success == true and correct == false`。与 baseline 按 sample ID 配对后：WTQ 共 22 个静默错误，审计检测到 13 个，检测率 59.09%；其中检测到后最终恢复正确 1 个，实际有修复轨迹且恢复正确 2 个；原本正确但被审计标记的 false positive 为 38 个，原本正确但 audit 最终变错的 repair degradation 为 8 个。TabFact 共 12 个静默错误，检测到 4 个，检测率 33.33%；检测到后恢复正确 2 个，实际有修复轨迹且恢复正确 3 个；false positive 为 24 个，repair degradation 为 8 个。

第一轮 audit 的错误层计数如下。注意一个样本可以在多个层报告错误，所以层计数不是样本数：WTQ 为 Operator 54、Parameter 35、Global 28；TabFact 为 Operator 20、Parameter 22、Global 3。最常见错误包括 WTQ 的错误目标列、缺失操作、缺失聚合、错误聚合、答案类型/基数不匹配和缺失排序；TabFact 的缺失排序、错误目标列、未知列、缺失操作、布尔极性和过滤参数错误。

第二轮 `outputs/100_cycle2_clean` 的结果用于验证迭代方向：WTQ baseline 65%、audit 70%、joint 83%；TabFact baseline 84%、audit 81%、joint 91%。WTQ audit 的提升说明更严格的 repair acceptance 和运行时语义警告对部分样本有帮助，但联合选择没有总体提升；TabFact joint 和 audit 均下降，说明当前 selector、布尔语义和参数 grounding 仍有误报风险。第二轮 WTQ audit 的三层错误计数为 Operator 54、Parameter 42、Global 34；TabFact 为 Operator 25、Parameter 21、Global 3。

## 七、剩余失败和下一步

当前最重要的剩余问题不是 Python 异常，而是正确执行后仍然选错答案。WTQ 主要集中在数字/日期/实体候选之间的选择、并列结果的基数、排名方向、持续时间表达和地名实体；TabFact 主要集中在否定句、比较边界、布尔候选的真假极性以及 Pandas Series 被直接作为答案返回。

当前 false positive 较高，说明审计器仍有过度报警。下一步最值得做的实验不是继续增加投票次数，而是建立 20–30 条按错误类型分层的固定开发集，分别比较 Global only、Global+Operator、Full hybrid 和 LLM-only；同时把参数 grounding 从“字符串是否出现在表中”进一步提升为列类型、行上下文、比较边界和答案来源联合验证。之后再在未参与调参的 100 条或更大测试集上运行一次，并报告检测率、修复成功率、误报率和准确率的共同变化。

论文结果目前只能称为 100 条受控实验结果，不能据此宣称超过 WTQ/TabFact 的 SOTA。下一步应先降低 false positive 和 repair degradation，再扩大到完整测试集，并保留所有 sample ID、日志和配置。
